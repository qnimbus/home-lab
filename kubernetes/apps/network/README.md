# network

Everything between a client and an app: the two Envoy Gateways every HTTPRoute attaches to, their wildcard certificates, DNS for both the LAN and Cloudflare, the Cloudflare Tunnel that carries WAN traffic, and Tailscale for remote access. `external-services` puts LAN devices that aren't Kubernetes workloads behind the same DNS.

## How it fits together

**Two Gateways.** `envoy-external` (`10.60.0.230`) and `envoy-internal` (`10.60.0.231`) both terminate TLS for every domain, and both are LAN-reachable. Their VIPs come from Cilium's LB-IPAM pool and are advertised over BGP (see `kube-system/cilium/config`). Only `envoy-external` is reachable from the WAN, through the tunnel. `envoy-internal` also has a raw-TCP `ssh` listener on port 22 for forgejo's git-over-SSH, LAN-only like the rest of it.

**DNS.** external-dns-unifi publishes every route on either Gateway, plus `external`/`internal.${DOMAIN_PROXII}` from the Gateways' own Services, so LAN clients go straight to the VIPs. external-dns-cloudflare only follows `envoy-external` (`--gateway-name`) and points each hostname at `external.${DOMAIN_PROXII}`, which the tunnel's `DNSEndpoint` CNAMEs to `<tunnel-id>.cfargotunnel.com`. Records are proxied (`--cloudflare-proxied`).

**WAN path.** Cloudflare edge → tunnel → cloudflared → `envoy-external` over HTTPS. cloudflared matches SNI to the Host and verifies the origin cert (`noTLSVerify: false`), so a domain whose certificate fails to renew hard-fails at the tunnel instead of passing silently. The `ClientTrafficPolicy` trusts `X-Forwarded-For` from the pod CIDR so Envoy sees the real client IP behind cloudflared.

**Tunnel ID substitution.** `${CLOUDFLARE_TUNNEL_ID}` comes from its own ExternalSecret (`cloudflare-tunnel-id`), not the plaintext `cluster-settings` ConfigMap. `tailscale-operator` does the same for `${TAILSCALE_USER}` (`tailscale-user`). Both set `substitution.flux.home.arpa/disabled` and list `cluster-settings` in their own `substituteFrom`: cluster-apps' patch replaces the whole list, and would drop the Secret.

### Certificates

cert-manager issues a wildcard for each of `${DOMAIN_APP}`, `${DOMAIN_CASA}`, `${DOMAIN_IO}`, `${DOMAIN_APPS}`, `${DOMAIN_CLUSTER}` and `${DOMAIN_DEV}` ([certificates.yaml](./certificates/export/certificates.yaml)). A `PushSecret` copies each one to a 1Password item of the same name, and keeps re-pushing (`updatePolicy: Replace`) so renewals get there too. `deletionPolicy: None` means removing the PushSecret never deletes the item.

On a rebuild, `certificates-import` restores them before the Certificates exist: `certificates-export` depends on it, an accepted exception to the structural-only `dependsOn` rule. The ExternalSecrets write the TLS Secret with cert-manager's own labels and annotations, so cert-manager adopts it instead of issuing a new one. It's one-shot: `refreshPolicy: CreatedOnce` stops ESO from overwriting cert-manager's renewals. `creationPolicy: Orphan` alone would not.

## Gotchas

- **Two-level domains aren't WAN-safe.** `${DOMAIN_CLUSTER}` and `${DOMAIN_APPS}` sit two levels under `vwn.io`, and Cloudflare's free Universal SSL only covers one level. The origin cert is fine, but the edge has none, so the handshake fails with `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` before the tunnel is reached. `${DOMAIN_APP}`, `${DOMAIN_CASA}`, `${DOMAIN_IO}` and `${DOMAIN_DEV}` are one level deep and would work; the naming convention puts new public routes on `${DOMAIN_APP}`, or on `${DOMAIN_DEV}` for a public view of the cluster itself.
- **`ExternalDNSStale` covers both external-dns instances.** The rule lives in [prometheusrule.yaml](./external-dns/cloudflare/prometheusrule.yaml) and matches any job; it catches a failing provider (an expired token, an API change) that crashes nothing.
- **Both external-dns instances read every `DNSEndpoint`.** What keeps a LAN device's record out of Cloudflare is `excludeDomains` in external-dns-cloudflare's [helmrelease.yaml](./external-dns/cloudflare/helmrelease.yaml). The zones on it all sit inside `${DOMAIN_IO}` or `${DOMAIN_PROXII}`, which that instance does publish, so a `DNSEndpoint` for a private address under any other name becomes a public, proxied record. A new LAN-only zone goes on that list before anything is named under it.
- **The public zones have a second writer, in another repo.** The hand-written records (mail, verification, anything that isn't a route) for every domain, including the five external-dns-cloudflare writes to, are managed with DNSControl in the private [qnimbus/dnscontrol](https://github.com/qnimbus/dnscontrol), checked out next to this repo as `../dnscontrol`. A `dnscontrol push` deletes whatever it doesn't declare, and only the `IGNORE` rules in its `dnsconfig.js` spare external-dns's records: `k8s.*` TXT (this instance's `txtPrefix`), CNAMEs to `external`/`internal.${DOMAIN_PROXII}`, `*.cfargotunnel.com` and `*.pages.dev`, and `_acme-challenge` TXT. A record of any other shape published from here needs an `IGNORE` there first.
- **`public-only` hides the tunnel alias from UniFi.** `external.${DOMAIN_PROXII}` has two answers on purpose: the gateway VIP on the LAN, the tunnel in Cloudflare. The tunnel's `DNSEndpoint` carries `external-dns.home.arpa/public-only: "true"` and external-dns-unifi runs with `--label-filter=external-dns.home.arpa/public-only!=true`. The filter covers all of that instance's sources, so it has to be the `!=` form: unlabelled routes, Services and `DNSEndpoint`s still match. Without it the instance still picks the VIP (a CNAME loses to any other record type) and logs a conflict every minute.
- **LAN devices are `DNSEndpoint`s** (`external-services`): several records in one object, an explicit record type, and no Service left behind. They used to be `ExternalName` Services with an IP in `externalName`, which only external-dns understands and which doesn't resolve in-cluster. Each device's Kustomization depends on both external-dns instances (see `flux-kustomization.instructions.md`).
- **The UDM's certificates are issued on the UDM, not here.** Two Let's Encrypt certificates, both through a Cloudflare DNS challenge, by two mechanisms. The console (`gateway.lan.home.${DOMAIN_IO}`, port 443) uses UniFi OS's built-in support (Control Plane > Console > Certificates), which serves the one certificate marked active and nothing else. The guest portal (`portal.guest.home.${DOMAIN_IO}`, port 8843) is outside its reach: it reads the Network application's own keystore, which [udm-le](https://github.com/kchristensen/udm-le) fills (`/data/udm-le`, `ENABLE_CAPTIVE="yes"`, a systemd timer at 03:00). udm-le is deprecated upstream and stays only for the portal. It also writes `/data/unifi-core/config/unifi-core.crt`, which the console falls back to when no built-in certificate is active. After a UniFi OS upgrade, `/data/udm-le/udm-le.sh force_deploy_certs` puts the portal certificate back if the upgrade reset it. The portal's hostname setting and its certificate have to change together.
- **wan-failover bypasses Envoy.** The router checks the Host header against its own IP, and Envoy Gateway can't rewrite Host to an IP literal (`URLRewrite.hostname` rejects it, `RequestHeaderModifier` silently drops `Host`). So the name points straight at the router, with no TLS.
- **`externalTrafficPolicy: Cluster`** on the Envoy Service dates from L2 announcements, where `Local` black-holed the VIP whenever the elected node had no Envoy pod. The VIPs are on BGP now; `Cluster` is still correct, and Cilium's DSR keeps the client IP.
- **`enableBackend: true`** in the envoy-gateway values turns on the `Backend` CRD (off by default), which lets an HTTPRoute target an off-cluster host with its own TLS settings instead of a Service with a hand-managed EndpointSlice.
- **doco-cd's webhook is the NAS's only public path.** The route matches `/v1/webhook` exactly, which doco-cd checks against GitHub's signature (`WEBHOOK_SECRET`). The same port also serves `/v1/api`, which can stop and remove stacks behind a plain API key: keep the match `Exact`, never a prefix. The webhook only speeds a deploy up; doco-cd still polls `main` when the cluster is down.
- **Home Assistant is the only device UI behind the gateway** (`ha.${DOMAIN_CLUSTER}`, an Envoy `Backend` + HTTPRoute), for the wildcard certificate. Its `http:` config has to set `use_x_forwarded_for` and list the node network (`10.60.0.0/24`) under `trusted_proxies`, or it answers 400. Not the pod CIDR: Cilium masquerades traffic that leaves the cluster, so Home Assistant sees a node address. The NAS is deliberately not proxied: the cluster's storage lives on it, so its UI must work when the cluster is down, and TrueNAS holds its own Let's Encrypt certificate for `nas.lan.home.${DOMAIN_IO}`.
- **cloudflared restarts on config changes** through Reloader. `config.yaml` is a `subPath` mount, which Kubernetes never updates in place.
- **Tailscale subnet router advertises `/23`s, not the `/24` LANs.** Tailscale's routes go in via ip rules evaluated before the main table, so a `/24` would beat the LAN route on machines already on that LAN and pull their local traffic through Tailscale. The `/23` loses on longest-prefix match there and still reaches Tailscale-only peers ([tailscale#1227](https://github.com/tailscale/tailscale/issues/1227), [overlapping subnets](https://tailscale.com/docs/reference/troubleshooting/network-configuration/lan-traffic-overlapping-subnets)).
- **The other half of that fix is on the gateway, not in Git.** The `/23` only helps a machine that sits on the advertised network. One on SkyNet (VLAN 10) reaches `10.60.0.0/24` through its default route alone, which the `/23` still beats. So SkyNet's DHCP hands out classless static routes: custom options 121 and 249 (the same payload under Microsoft's older code), value `18:0A:3C:00:0A:0A:00:01:00:0A:0A:00:01`, which is `10.60.0.0/24` via `10.10.0.1` plus the default route via `10.10.0.1`. The default route has to be in there, because a client that gets option 121 ignores the plain router option. Only SkyNet carries the options; remove them and LAN machines running Tailscale send cluster traffic through the tunnel again.
- **Tailscale exit node** needs approving per device in the admin console, or an `autoApprovers` ACL rule, before clients can pick it.
- **`cluster-admin` for `${TAILSCALE_USER}`** is meant for kubectl through the operator's API-server proxy, gated by tailnet ACLs instead of a distributed kubeconfig. The proxy is off (`apiServerProxyConfig.mode` isn't set, and the chart defaults it to `"false"`), so the binding does nothing until that is turned on.
- **external-dns-unifi owns the `DNSEndpoint`/`DNSRecord` CRDs.** Both releases install the same chart, which ships them in `crds/` with no value to turn them off, so external-dns-cloudflare carries `crds.flux.home.arpa/disabled: "true"` and skips them. That's also why cloudflare-tunnel, whose `DNSEndpoint` needs the CRD, depends on external-dns-unifi.
- **Shared 1Password items.** `cloudflare-tunnel` feeds the tunnel token, the tunnel ID and external-dns's `API_TOKEN`; `tailscale` feeds the operator's OAuth client and `USERNAME`; `unifi` is also read by apps outside this namespace. Rename a field and check every consumer: `grep -rn "key: <item>" kubernetes`.
