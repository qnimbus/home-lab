# default

Personal apps with no better home: finance, documents, git, a pastebin, the dashboard and the guest-WiFi voucher portal. They share nothing beyond the namespace. Each app with a database gets its own CNPG cluster from [`components/postgres`](../../components/postgres/README.md), except wallos and wastebin, which keep SQLite on their volume, and every route is on `envoy-internal` except whoami's.

## How it fits together

**Scale to zero over HTTP.** firefly-importer and unifi-voucher-site use [`components/keda/http-scaler`](../../components/keda/http-scaler/). Their HTTPRoute points at `keda-add-ons-http-interceptor-proxy` in `system`, not at the app's Service, so the interceptor can hold the first request while the pod starts. Meanwhile the `InterceptorRoute` serves a self-refreshing 503 page. It scales on `requestRate`, not concurrency: the placeholder answers in microseconds, so a concurrency gauge is back at 0 before the scaler polls, and scale-up never fires. Their `ks.yaml` depends on `keda-add-ons-http`, because bootstrap doesn't pre-install the `InterceptorRoute` CRD.

**paperless, paperless-gpt and mail-archiver follow the NAS.** [`components/keda/smb-scaler`](../../components/keda/README.md) scales paperless and paperless-gpt to zero while blackbox-exporter's `${NAS_HOST}:445` probe fails, and `components/keda/nfs-scaler` does the same for mail-archiver on `${NAS_HOST}:2049`. That is each one's only scaler: KEDA allows one ScaledObject per workload. Every KEDA-scaled HelmRelease here ignores `/spec/replicas` in drift detection; without that, Flux would put the replicas back within the hour.

**paperless storage.** The archive (`consume`, `export`, `media`) and backups live on the NAS `Archive` and `Backup` SMB shares, as static PVs in [pv.yaml](./paperless/app/pv.yaml):

- They use `Retain`, so deleting the PVC or the app never touches the documents.
- `storageClassName: smb` is only a matching label, since csi-driver-smb is driver-only and no `smb` StorageClass exists. The PVC must still repeat it: it's compared even when `volumeName` is set.
- Each `volumeHandle` must be unique cluster-wide.
- The mount credentials are `system/smb-credentials`. The `csi-driver-smb` Kustomization that creates them has `wait: true`, which is what the `dependsOn` here relies on.

Gotenberg and Tika run as sidecars in the same pod and are reached over `localhost`.

**paperless AI index.** paperless embeds documents through the NAS's `llama-embedding` server (`https://embeddings.${DOMAIN_APP}/v1`, see [`docker/nas/10-llama`](../../../docker/nas/10-llama/README.md)). `PAPERLESS_AI_LLM_EMBEDDING_MODEL` must match that server's preset section name. Changing the model means rebuilding the index (`document_llmindex rebuild` in the `app` container), as vectors from different models don't compare. AI suggestions and chat use the NAS's `llama-server` (`https://llama.${DOMAIN_APP}/v1`); `PAPERLESS_AI_LLM_MODEL` is again a preset section name. That server runs on demand (`just docker llama-start`): while it's stopped, suggestions and chat return an error, but indexing keeps working. `PAPERLESS_AI_LLM_OUTPUT_LANGUAGE: nl-nl` makes paperless rewrite each suggestion's title, tags, document types and storage paths in Dutch with a second LLM call; without it, paperless uses the user's UI language. It is one language for every document, English ones included. Correspondents and dates are never translated.

**paperless-gpt.** It suggests a title, tags, correspondent, document type and created date for each document tagged `paperless-gpt`, and applies them once approved in its UI. It talks to paperless through the in-cluster Service (`http://paperless:8000`) with the token of a dedicated paperless superuser, `paperless-gpt` (1Password item `paperless-gpt`, field `API_TOKEN`), so paperless's history shows its changes under that name. Every LLM call goes to the NAS's `llama-server` through its OpenAI-compatible API (`LLM_PROVIDER: openai`, `OPENAI_BASE_URL` with `/v1`). `LLM_MODEL` is a preset section name, and `OPENAI_API_KEY` is a placeholder that only has to be non-empty. Its metadata requests queue behind paperless's own AI suggestions on the same single-slot model. The scaler is paperless's: it has no use for the NAS's SMB shares itself, but it is useless without paperless and the NAS's LLM, so it scales to zero with them. A start before paperless is up only logs warnings.

Metadata suggestions only, no automation: nothing processes the `paperless-gpt-auto` tag.

**paperless-gpt's LLM OCR** reads each page as an image with `GLM-OCR` (`VISION_LLM_MODEL`), a 0.9B OCR model on the same `llama-server`, loaded next to Qwen3.6 (`--models-max 2`, see [`docker/nas/10-llama`](../../../docker/nas/10-llama/README.md)), so OCR doesn't wait for or evict the metadata model. It runs for a document tagged `paperless-gpt-ocr-auto`, or from the OCR page in its UI, and writes the text straight into the document's content in paperless, with no review step. The PDF itself keeps paperless's Tesseract text layer, so search finds the new text but copying from the PDF gives the old one. `ocr_prompt.tmpl` is just `OCR`, the trigger GLM-OCR is trained on; paperless-gpt's default prompt is a long instruction plus the existing text, which a specialist model doesn't follow. `OCR_LIMIT_PAGES: "0"` reads every page: with the default of 5, a longer document's content would be replaced by the text of its first five pages. `IMAGE_MAX_RENDER_DPI: "300"` (default 600) is plenty for text and keeps the page images small.

The tags it uses in paperless are `paperless-gpt` (created by hand, removed again when a suggestion is applied), `paperless-gpt-ocr-auto` (the OCR trigger, removed again once the text is written) and `paperless-gpt-failed` (created at startup, set when paperless rejects part of an update, or when a document's OCR failed `OCR_MAX_RETRIES` times). `AUTO_TAG_COMPLETE: ""` stops it creating `paperless-gpt-auto-complete`, which only automatic metadata uses. `PDF_OCR_TAGGING: "false"` stops it marking OCR'd documents `paperless-gpt-ocr-complete`, a tag auto OCR then skips: without it, tagging a document `paperless-gpt-ocr-auto` again OCRs it again. The tags in use must be in the metadata script's `keep_tags`, or its apply removes them.

The five metadata prompts are Dutch and live in [app/resources](./paperless-gpt/app/resources/), next to `ocr_prompt.tmpl`. Each of the six is mounted read-only over its file in `/app/prompts`, and the app copies the other defaults (custom fields, ad-hoc analysis) into an `emptyDir` underneath at every start. An edit in the Settings page fails for the six, and is lost at the next restart for the rest. They hand the model the existing tags, correspondents and document types to choose from, and all start with the same block holding the document text, so llama.cpp reuses that cached prefix across a document's five calls. The volume (`/app/config`, `/app/db`, kopiur-backed) keeps the Settings page's values and the undo history of applied suggestions.

**Firefly III.** The importer calls Firefly through its in-cluster Service. `VANITY_URL` is the browser-facing URL for anything sent to the user, like the OAuth redirect. The `firefly-cron` CronJob calls `/api/v1/cron/<STATIC_CRON_TOKEN>` hourly. Firefly needs this at least daily for recurring transactions, bills and auto-budgets. Both apps read the 1Password `firefly-III` item.

**homepage** discovers services from the `gethomepage.dev/*` annotations on HTTPRoutes across the cluster, so a new app shows up by annotating its route. For that it needs a read-only ClusterRole and `automountServiceAccountToken: true`, which chart v5 defaults to false. Its MCP endpoint is on, authenticated by `HOMEPAGE_MCP_TOKEN` because there's no session auth. It's read-only because `/app/config` is a ConfigMap mount.

## Operating

```bash
just k8s db-backup default <app>                    # manual CNPG backup
just k8s database dump default <app> "" <db>        # "" = default file under ~/cnpg-backups
just k8s database restore default <app> <file> <db>
just k8s browse-pvc default <claim>
```

`dump`/`restore` default `db` to the app name, which every database here matches. `just` arguments are positional only: `db=firefly` would be taken as the file name.

## Gotchas

- **mail-archiver's probes send a `Host` header.** `AllowedHosts` makes the app answer `400` to any other host, the pod IP a probe uses by default included. They hit `/Auth/Login`, because `/` redirects to the route's hostname, which the kubelet reports as a probe warning.
- **mail-archiver keeps everything in Postgres**, attachments included, so `POSTGRES_STORAGE` is sized for the mail. It can't be raised in place: `openebs-hostpath` doesn't expand volumes, so a larger size means rebuilding the cluster from its backup. For the same reason its S3 base backups run weekly (Sunday 02:18 UTC) with a 7-day window (`POSTGRES_BACKUP_RETENTION`), so B2 holds two full copies instead of one per day. The NAS dump still runs nightly.
- **mail-archiver mounts `apps/mail-archiver` under the NAS export `/mnt/tank/Cluster/backup`**, the export Plex and the downloads apps use, which squashes every client to a NAS user. `data` holds ASP.NET's DataProtection keys, which sign the login cookies: losing them logs everyone out and nothing more. `import` is `/data/import`, the only folder the CLI imports (`--import-mbox`, `--import-eml`) may read: put the files there on the NAS and run the import in the `app` container. The key that encrypts the stored mailbox passwords is `CREDENTIAL_ENCRYPTION_KEY` in 1Password: without it those passwords have to be entered again.
- **mail-archiver writes to `/app/uploads` and `/app/exports`** at startup and crashes on a read-only root filesystem without them. Both are scratch, on an `emptyDir` with `/tmp`: an mbox upload (up to 10 GB) lands on the node's disk until it is imported.
- **mail-archiver's database connection string is assembled in `env`** from the CNPG Secret with `$(DB_PASSWORD)`. Kubernetes only expands variables defined earlier in the list, which the `dependsOn` on that entry arranges.
- **paperless `PAPERLESS_FILENAME_FORMAT`**: app-template runs env values through Helm's `tpl`, so Jinja's `{{ }}` must be written `{{"{{"}} … {{"}}"}}`. Unescaped, the HelmRelease fails to render and the old pod silently keeps running. `{% %}` needs no escaping.
- **paperless starts as root** (container `securityContext`). The s6-overlay init installs `tesseract-ocr-nld` for `PAPERLESS_OCR_LANGUAGES` and chowns the volumes; both fail as non-root. `USERMAP_UID`/`USERMAP_GID` then drop the app processes to 1000. It keeps the runtime's default capabilities, an accepted exception to the drop-`ALL` pattern for root-starting images.
- **paperless's `gotenberg` sidecar runs as 1001**, the image's own `gotenberg` user, not the pod's 1000. As 1000 it has no passwd entry, so `HOME` is `/`, which isn't writable, and Chromium fails to start (`chrome_crashpad_handler: --database is required`): every email-to-PDF conversion returns `500`.
- **paperless v3** needs `PAPERLESS_DBENGINE` set explicitly (it was inferred from `DBHOST` before).
- **paperless `PAPERLESS_OCR_MODE: redo`**: the Canon MF750C embeds its own OCR text layer in every scan, and in the default `auto` mode paperless keeps any PDF's existing text, so Tesseract (with `nld`) would never read a Canon scan. `redo` replaces an existing OCR layer and keeps the real text of born-digital PDFs. It can't be combined with deskew: slightly tilted pages stay tilted in the archive copy (sideways and upside-down pages are still turned). Documents consumed before this setting only get the new OCR when reprocessed (bulk edit → Reprocess). A value on paperless's Configuration page (OCR settings) overrides every `PAPERLESS_OCR_*` variable, so leave those fields empty there.
- **paperless's OCR memory: `PAPERLESS_THREADS_PER_WORKER: "4"` and an 8 GiB limit on `app`.** Unset, paperless divides the CPUs it sees by `PAPERLESS_TASK_WORKERS`, and in the pod it sees all 32 of the node's cores: 16 OCR threads per worker. OCRmyPDF renders every page to an image and runs one Tesseract per thread, so workers × threads is the number of pages OCR'd at once; 2 × 4 = 8 peaks at roughly 2.5 GiB in a bulk reprocess. A single PDF can still need far more: one with images embedded at thousands of DPI made one worker process grow past 3 GB on its own. The limit leaves room for that, as an out-of-memory kill takes down the whole container, web UI and task queue included (the Tasks page then shows the tasks that were running as stuck in "started"). Raise workers or threads only together with the limit.
- **paperless's Dragonfly has no auth.** With no NetworkPolicy, any pod in the cluster can reach it on `6379`.
- **paperless-gpt has no authentication.** Anyone who can reach `envoy-internal` can read document text in its UI, apply changes with its paperless token and start LLM jobs. Put a login in front of it before the route is widened.
- **paperless-gpt's token belongs to a superuser.** paperless shows a non-superuser only the documents, tags, correspondents and types it owns or was granted, even with global view permissions. A plain user sees none of the existing ones, and paperless-gpt then tries to create duplicates.
- **paperless-gpt's prompts must answer `Unknown`**, in English, when nothing fits. That word (or `none`, `n/a`) is what leaves a correspondent unchanged, and it is no valid date or document type, so neither changes either. Any other correspondent name the model returns is created in paperless on apply: no setting stops it, so the prompt limits the model to the existing list. Document types and tags are only ever picked from the existing lists (`CREATE_NEW_TAGS` stays at its default, off).
- **paperless-gpt keeps a document's tags.** It adds the current tags back to every suggestion, so the model can add tags but never drop a wrong one: remove that in the review UI. Only the title and tag prompts see the current metadata (`{{.Title}}`, `{{.OriginalTags}}`); the correspondent and document type prompts get the document text and the new title only.
- **paperless-gpt never touches storage paths**: it has no such field, so `PAPERLESS_FILENAME_FORMAT` keeps deciding where a document lives. A created date is only suggested when the document states a full date, and the review UI's "Created date" checkbox can switch it off per run. paperless logs `created_date is deprecated` for every date paperless-gpt sets; it still accepts it.
- **Reprocessing in paperless erases LLM OCR text.** Reprocess runs paperless's own OCR again and overwrites the content paperless-gpt wrote, without a warning. Don't reprocess a document that has LLM OCR text, or tag it `paperless-gpt-ocr-auto` again afterwards.
- **A vision model can invent text where a scan is unreadable**, where Tesseract leaves garbage. Compare a few bad scans by hand before tagging many documents at once.
- **paperless-gpt sends `temperature: 0`** on every metadata request: the OpenAI client always sends one, and paperless-gpt offers no setting for it (`LLM_TEMPERATURE` is Ollama-only). That overrides the preset's 0.7, which suits classification; `top_p` is not sent, so the preset's 0.8 applies.
- **paperless-gpt has no `TOKEN_LIMIT`.** Setting one makes it count tokens with tiktoken, which downloads its vocabulary from `openaipublic.blob.core.windows.net` at the first count. Without it the whole document goes to the model, and a document beyond the 32k context fails with an error from `llama-server` instead of being cut short. `VISION_LLM_MAX_TOKENS` triggers the same download for LLM OCR.
- **Long startup probes** (`failureThreshold: 60`) on firefly and paperless cover first-boot migrations and search-index builds.
- **paperless's `paperless` PVC holds only derived data**: the search index, the classifier model and scheduler state. Everything else is in Postgres and on the NAS. An empty volume is recoverable with `document_index reindex` and `document_create_classifier`, run in the `app` container.
- **forgejo** leaves `image.tag` unset so it follows the pinned chart's `appVersion`. `cache`/`queue`/`session` are unset too, so the chart falls back to in-memory, which is fine for one replica.
- **unifi-voucher-site** has `AUTH_DISABLE: "true"`. That's only acceptable while it's internal-only; revisit it if the route is ever widened. Its secret reshapes the shared 1Password `unifi` item (full-URL `UNIFI_HOST` to bare `UNIFI_IP`/`UNIFI_PORT`, `API_KEY` to `UNIFI_TOKEN`). All other settings are listed in the [upstream README](https://github.com/glenndehaan/unifi-voucher-site).
- **wallos starts as root** and has a writable root filesystem. Its `startup.sh` runs `usermod`, chowns `/var/www/html` and the volumes to `www-data` (82), and starts nginx on port 80 and crond; php-fpm then serves as 82. The container keeps only the capabilities that needs (`capabilities.add`). The kopiur mover runs as 82 to match the files.
- **wallos refuses SMTP, webhook and OIDC hosts that resolve to a private address** unless they're on its SSRF allowlist. `SSRF_ALLOWLIST` lists [`mail/smtp-relay`](../mail/smtp-relay/) as `smtp-relay.mail.svc.cluster.local:25`, matching the host and port in the notification settings. The variable replaces the allowlist in Admin → Security Settings, which it also locks, so add any other private host (a self-hosted webhook target) here, comma-separated.
- **wallos runs its own cron** inside the container (payment dates, exchange rates, notifications at 09:00). It follows `TZ`, which is `${CLUSTER_TIMEZONE}`: the dates and notification times are local.
- **whoami** listens on 8080 so it can run as non-root; its Service keeps port 80.
